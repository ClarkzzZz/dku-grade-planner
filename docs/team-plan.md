## 1. 我们要做什么

做一个面向 DKU 学生的 Java 图形应用。用户根据 syllabus 录入考核类别和权重，再逐次添加作业、quiz 等成绩。程序计算各类别当前平均分，并根据用户的目标总分及其他类别的预计最终成绩，反推期末考试需要多少分。

一句话介绍：

> 把零散的 homework、quiz 和考试成绩汇总起来，帮助学生看清当前表现，并计算达到目标总分还需要怎样的成绩。

第一版只管理一门课，支持编辑、保存和加载。不做账号、联网、dashboard 对接或 syllabus PDF 自动解析。

## 3. 先统一计算规则

这是三个人开始写代码前最需要达成一致的部分。否则容易出现界面和算法对“当前成绩”的理解不同。

### 3.1 单次成绩

每个条目记录得分 `earnedPoints` 和满分 `maxPoints`。已评分时：

```text
条目百分制成绩 = earnedPoints / maxPoints × 100
```

基础版规定满分必须大于 0，得分在 0 到满分之间，不支持超额加分。

未评分的得分为“空”，不是 0。已评分且得分为 0 必须正常参与计算。

### 3.2 同一类别的汇总

**方式 A：每条等权。** 先将各条换成百分制，再求平均。

**方式 B：按总点数。** 所有已评分条目的总得分除以总满分，再换成百分制。

例如 HW1 为 8/10，HW2 为 90/100：

| 方式 | 计算 | 类别平均分 |
|---|---|---:|
| 每条等权 | `(80 + 90) / 2` | 85 |
| 按总点数 | `(8 + 90) / (10 + 100) × 100` | 约 89.09 |

没有已评分条目时，类别平均分显示“暂无成绩”，不能显示为 0。

### 3.3 当前表现与确定贡献分开显示

Homework 当前平均 90，不代表课程总分已经确定拿到 9 分：后面还有作业时，类别最终平均仍可能改变。

基础版采用保守且容易解释的方式：

- **未结束类别**：显示当前已评分条目平均分，不把该类别全部权重算作已确定贡献。
- **已结束类别**：用最终类别平均分乘权重，计入确定贡献。
- **已结束类别加权平均**：确定贡献除以已结束类别的权重总和。没有已结束类别时显示“暂无”。
- **预计课程总分**：根据已结束类别成绩和未结束类别预计成绩计算，明确标注为预测。

这里的“确定贡献”以用户将类别标为结束、输入正确为前提。基础版不尝试在类别尚未结束时推导部分已锁定分数，因为这需要知道所有未来条目的数量和权重。

不要把“确定贡献总和”直接标为“当前总成绩”，以免让用户误解。

### 3.4 目标反推

每次只选择一个待反推类别，例如 Final exam。基础版要求它只有一个考试条目、尚未结束、且权重大于 0。

其他类别的成绩取值规则：

1. 已结束类别使用实际最终平均分。
2. 未结束类别使用用户明确确认的预计最终平均分。
3. 可以提供“复制当前平均分”按钮，但不能静默把当前表现当作最终成绩。
4. 缺少其他类别的预计值时，提示补齐，暂不计算。

权重在界面以百分数录入，算法中先除以 100 转成比例：

```text
其他类别贡献 = Σ（其他类别最终或预计平均分 × 对应权重比例）
所需考试分数 =（目标总分 - 其他类别贡献）/ 待反推考试权重比例
```

示例：Homework 预计 90、Quiz 预计 85、Midterm 实际 80、Final project 预计 90，目标 85：

```text
其他贡献 = 90×0.10 + 85×0.20 + 80×0.25 + 90×0.15 = 59.5
期末要求 = (85 - 59.5) / 0.30 = 85
```

### 3.5 结果解释

| 所需成绩 | 界面说明 |
|---|---|
| 大于 100 | 在其他成绩假设不变时，目标无法达到；显示期末满分时的总分 |
| 大于 0 且不超过 100 | 显示达到目标所需的考试成绩 |
| 小于或等于 0 | 在其他成绩假设不变时，期末 0 分也达到目标 |

不把“期末 0 分也能达到目标”写成“不用参加考试”。课程可能另有参加考试或通过要求，本工具不判断这些规则。

内部保留计算精度，展示时统一保留两位小数。若显示“至少需要”且只展示两位小数，应向上取到两位，避免把实际要求向下舍入。真实考试按整数或固定点数给分时，百分制门槛仅供参考，不保证可取得每个小数值。

## 5. 开发前约定的接口

下面是建议接口，第一天由三人确认后统一使用，不代表必须照搬每个方法名。

### 5.1 数据约定

| 字段 | 约定 |
|---|---|
| 课程名称 | 非空字符串 |
| 类别 / 条目 ID | 稳定且唯一的字符串；名称变化时 ID 不变 |
| 类别名称 | 非空；基础版可要求同课程内不重复 |
| 类别权重 | 0–100 的百分数，全部类别合计 100 |
| 得分 | `Double`，`null` 表示未评分，`0.0` 表示零分 |
| 满分 | 大于 0 |
| 类别完成状态 | 用户明确设置；完成时所有条目都必须已评分且至少一条 |
| 预计类别成绩 | 百分制 0–100，仅用于预测，不写入真实得分 |

编辑过程中权重暂时不等于 100 是正常的：可以保留草稿，但禁止显示正式总分和目标反推结果，提示还差多少或超出多少。

### 5.2 计算接口示意

```java
OptionalDouble calculateCategoryAverage(GradeCategory category);

double calculateFinalizedContribution(Course course);

CalculationResult calculateRequiredScore(
    Course course,
    String targetCategoryId,
    double targetOverallScore,
    Map<String, Double> expectedCategoryScores
);
```

`calculateFinalizedContribution` 应在数据通过校验后调用。它返回已结束类别对课程总分的贡献，不是所有已录入条目的总体平均。

`expectedCategoryScores` 用类别 ID 作键。已结束类别忽略预测值，始终使用实际成绩。预测值只保留在情景中，不修改成绩记录。

结果至少区分：正常可达、期末 0 分已足够、超过 100 无法达到、输入不完整或非法。B 不应在界面重新实现一套公式。

### 5.3 校验与存储接口示意

```java
List<ValidationIssue> validateForCalculation(Course course);

void save(Course course, Path path) throws IOException;

Course load(Path path) throws IOException;
```

校验包含“对象位置 + 错误原因”，例如“Quiz / Quiz2：得分不能超过满分”。输入控件可提前检查，但核心服务也应有校验，防止加载文件绕过 GUI。

加载时先读取临时对象并校验，成功后再替换当前课程。失败时保留当前数据并提示原因。

### 5.4 存储建议

为了减少外部依赖，基础版可以使用 Java `Properties` 的 XML 保存与读取方式，由 C 定义固定字段和索引。保存课程、类别、条目和格式版本，不保存能重新计算得到的平均分。

需要验证中文、特殊字符、未评分空值和条目顺序能正确恢复。GUI 里保存的预测情景可以作为可选内容，不应与真实成绩混在一起。

如果你们已经熟悉 JSON 库，也可以改用 JSON，但必须在项目中说明依赖和启动方式。CSV 批量导入是扩展，不是基础版的前提。


## 7. 数据结构怎样体现课程内容

| 结构 | 用在哪里 | 为什么适合 |
|---|---|---|
| `List<GradeCategory>` | 课程中的类别 | 保留显示顺序，支持增删和遍历 |
| `List<GradeEntry>` | 每类的多个作业或 quiz | 条目数量可变，便于计算和编辑 |
| `Map<String, Double>` | 预测情景中的类别预计成绩 | 按稳定 ID 查找对应预测值 |
| `Set<String>`，可选 | 校验 ID 或名称重复 | 去重和成员检查 |

List 和 Map 已能支撑主要功能。不要为了凑结构而引入没有实际作用的 Queue、Tree 或 Heap。

报告中可以解释：为什么预测按类别 ID 查找而不是按界面行号；为什么真实条目和预测值分别保存；类别汇总需要遍历已评分条目，时间开销随条目数量线性增长。

如果老师另有自行实现结构的要求，再调整；当前项目文档未明确要求全部自行实现。
